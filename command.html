Release Commands

Every update goes the same way: change the code, commit, push, then push a version tag. GitHub Actions builds Windows, macOS and Linux and publishes the release.

Run all commands in C:\Users\Manjeet\Use-As-Server (Command Prompt, PowerShell or Git Bash).

The everyday loop

Use this after every change, whether or not you release. Always pull before you push, because edits made on the GitHub website make a plain push fail.

  1. See what changed:

    git status git diff

  2. Stage the files you changed. Name them, or use a folder; avoid git add -A unless .venv/ is in .gitignore:

    git add useas_server index.html packaging

  3. Commit with a short message that says what the change does:

    git commit -m "Add per-app volume on Linux"

  4. Get GitHub's latest changes, then push yours:

    git pull --rebase --autostash git push

  5. Check it arrived: git log --oneline -5 should show your commit on top, next to origin/main.

The LF will be replaced by CRLF warnings are only about Windows line endings; ignore them.

Releasing a new version

A release is one pushed tag. Push your commits first (the everyday loop), then tag the latest commit.

ChangeExampleNew version
Bug fix onlyLinux crash fix2.1.1 → 2.1.2
New featurePer-app volume on Linux2.1.1 → 2.2
Big change, phone app must update tooNew protocol2.x → 3.0

Tag and push it:

git tag v2.2 git push origin v2.2

The workflow writes the version into the app, the installer and the file names by itself; you don't edit APP_VERSION or my.iss. Watch it in GitHub › Actions (about 20–30 minutes). When every job is green, the release Use As Server 2.2 is marked Latest with 8 files:

LinuxUseAsServer_v2.2_linux_amd64.deb, UseAsServer_v2.2_linux_x86_64.rpm, UseAsServer_v2.2_linux_x86_64.tar.gz, UseAsServer_v2.2_x86_64.flatpak

The app's Check for Update and the website both read the Latest release, so users see it straight away. Add a few lines of release notes afterwards: open the release › pencil icon › write at the top › Update release.

See your tags with git tag (local) or git ls-remote --tags origin (GitHub).

Test builds without a release

Try a change on real Windows, Mac or Linux builds before users get it: GitHub › Actions › Build Use As Server › Run workflow. Push your commits first; it builds what is on GitHub.

OptionWhat to pick
versione.g. 2.2 (empty = APP_VERSION in useas_server/common.py)
platformsall, or just windows, linux or macos to save time
flatpakon to also make the Flatpak (needs Linux)
releaseoff for a test; on publishes release v<version>

When it finishes, download the files at the bottom of the run's page under Artifacts. Each one is a .zip with the file inside.

The Linux build also opens the window on a virtual screen and installs the .deb on Ubuntu and the .rpm on Fedora. A red X there means the build would crash or not install, so don't release it.

Resolving a conflict

During git pull --rebase, --theirs means your commit and --ours means GitHub's version (it's reversed from what the words suggest).

git checkout --theirs index.html git add index.html git rebase --continue git push

Use --ours instead to keep GitHub's version. Repeat for each file the message names. To back out completely: git rebase --abort.

Moving a tag after a failed build

git tag -f v2.2 git push -f origin v2.2

This points the tag at your newest commit and starts the build again.

Deleting a tag you didn't mean to push

git tag -d v2.2 git push origin --delete v2.2

If a release was already made for it, delete the release on GitHub too (Releases › the release › trash icon).

Undoing local changes (before pushing)

ToRun

Undo the last commit but keep its changesgit reset --soft HEAD~1
Fix the last commit's messagegit commit --amend -m "Better message"

Once a commit is pushed, don't undo it with reset; make a new commit that fixes it instead.

Website and icons

The website is index.html in the repository root, served by GitHub Pages. Its download buttons find the newest release's files by themselves, so a release needs no website edit.

Update it only when the text changes (a new feature, a new setup step), then commit and push as usual:

git add index.html git commit -m "Website: explain per-app volume" git pull --rebase --autostash git push

The live site updates in a minute or two; press Ctrl+F5 if you still see the old page. Optionally change the v2.1.1 file names in it to the new version: they're only used when the page can't reach GitHub.

New icon

After changing icon.png (2048 × 2048), rebuild every icon size (Windows .ico, Mac, Linux menus, website) and commit them:

python packaging/icons/make_icons.py git add icon.ico packaging/icons git commit -m "New icon"
